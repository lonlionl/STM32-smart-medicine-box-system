# tools

本目录存放工程自用的辅助脚本。内容分两部分：目录内各个脚本的用途，以及设备端源码的编码约定。

## 目录内容

| 文件 | 用途 |
|---|---|
| `gen_font.py` | 生成 LCD 字库：从系统中文字体渲染点阵，输出 `User/BSP/font.c` 与 `font.h` |
| `verify_numbers.py` | 复核代码中的常量：CRC32 查找表与算法、结构体尺寸、PWM 预分频、舵机角度换算 |
| `show.py` | 带行号打印 GBK 源码，供阅读与检索使用 |
| `README.md` | 本文件 |

## 源码编码约定

设备端 `User/` 下 30 个 `.c/.h` 统一使用 GBK（代码页 936），无 BOM。

### 为什么必须是 GBK

Keil 工程关闭了 C99（`Project/yehuoF103.uvprojx` 中的 `<uC99>0</uC99>`）。armcc V5 在中文 Windows 上按系统代码页读取源文件字节：

| 源文件编码 | armcc V5（C99 关闭）的表现 |
|---|---|
| GBK | 中文注释按 GBK 正确解析，编译通过 |
| UTF-8 | 汉字的字节序列被当作 GBK 解析，注释显示为乱码，或直接报 `invalid multibyte character` 编译失败 |

若需要使用 UTF-8 源码，必须开启 `--c99` 或指定 `--locale`。本工程未开启这些选项，因此 GBK 是唯一稳定可用的选择。

### 编码不匹配的后果

GBK 汉字占两个字节。用 UTF-8 编辑器保存 GBK 文件后，解码失败的字节会被写成 `?`，且不可逆——原本的中文注释无法从文件内容恢复，只能依据上下文重写。

工程开发期间遇到过两处此类损坏：`lcd.c` 与 `main.c` 的注释退化为 `?`，`menu.c` 有 17 行注释损坏。两处均已按上下文重写为准确内容。

结论：修改这些文件前先确认编码。不确定时使用可显式指定编码的脚本按字节读写，不要用默认按 UTF-8 保存的编辑器直接编辑。

### 字符串字面量的写法

界面显示用的中文一律写成字节转义形式：

```c
/* 推荐：编译结果与编辑器保存方式无关 */
#define STR_TITLE "\xD6\xC7\xC4\xDC\xD2\xA9\xCF\xE4\xCF\xB5\xCD\xB3"   /* 智能药箱系统 */

/* 不推荐：结果取决于源文件编码 */
#define STR_TITLE "智能药箱系统"
```

这些字符串最终要按 GBK 字节送进字库查字形，显式写字节码可以消除对源文件编码的依赖。`main.c` 与 `menu.c` 中的界面字符串都采用这种写法。

## 添加界面中文的流程

字库是按需生成的，只收录界面真正用到的汉字。新增或修改界面文案时：

1. 把新文案加入 `gen_font.py` 的 `UI_STRINGS` 列表；
2. 重新运行 `python tools/gen_font.py`，它会重写 `font.c` 与 `font.h`；
3. 在 Keil 中重新编译。

漏掉这一步的后果是那个汉字在屏上显示为空白：字形查不到时渲染函数会跳过绘制但仍推进光标，既不报错也不崩溃。字库规模直接占用 Flash，新增一个 16×16 汉字约 36 字节，工程当前占用接近 Keil 评估版 32 KB 上限，扩充字库前需确认余量。

## 注释约定

- 函数使用块注释，写清作用、参数、返回值，以及实现原理与设计取舍，而非复述代码字面行为。
- 关键宏与全局变量注明用途、单位、取值范围，以及特殊值的含义（例如 `hour == 0xFF` 表示该时间点未设置）。
- 行内注释解释为何采用某种写法，特别是非直观的处理。
- 硬件与协议层面的约束在对应代码处注明，例如 ESP-01S 单条 MQTT 报文 512 字节上限、片内 Flash 页擦除单位 2 KB。
- `font.c` 与 `font.h` 由脚本生成，不手工编辑；需要改动时修改 `gen_font.py`。
