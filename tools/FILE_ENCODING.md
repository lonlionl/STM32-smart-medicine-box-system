# 设备端源码编码规范

## 结论：**全工程统一 GBK**（无 BOM，LF 换行）

`User/` 下全部 30 个 `.c/.h` 文件现在都是 **GBK（代码页 936）** 编码。

## 为什么必须用 GBK，不能用 UTF-8

本工程 Keil 设置里 **C99 是关闭的**（`<uC99>0</uC99>`，见 `Project/yehuoF103.uvprojx`）。
armcc V5 在中文 Windows 上按**系统代码页（936/GBK）**读取源文件字节：

| 源文件编码 | armcc V5（C99 关闭）的表现 |
|---|---|
| **GBK** | 中文注释按 GBK 解析，正常显示，编译通过 ✅ |
| UTF-8 | 汉字的多字节序列被当成 GBK 解析，轻则注释乱码，重则报 `invalid multibyte character` 编译失败 ❌ |

想用 UTF-8 源码，需要开 `--c99` 或加 `--locale=...` 等编译选项；本工程没有开，所以统一 GBK 是最稳的选择。

## 改文件前必读：历史上踩过的坑

项目早期是 **GBK 与 UTF-8 混编**（GBK 17 个 / UTF-8 14 个），因此发生过两次事故：

1. **`lcd.c` 与 `main.c`**：用 UTF-8 编辑器保存了 GBK 文件，GBK 汉字每字 2 字节，
   按 UTF-8 解码失败后字节被替换成 `?`，「显示驱动」退化成 `??????`。
   **字节已丢、不可逆**，只能按上下文重写（现已重写为准确的中文/英文注释）。
2. **`menu.c`**：同样原因造成 17 行注释损坏（现已在补中文注释时一并重建）。

**教训**：改这些文件前先确认编码；不确定就用能显式指定编码的脚本按字节读写，
不要用默认按 UTF-8 保存的编辑器直接改。已统一为 GBK 后，这个问题从根上消除了。

## 字符串字面量的写法（重要约定）

界面中文**不要直接写汉字**，而是写成字节转义：

```c
/* 好：不管编辑器怎么存文件，编译结果都一样 */
#define STR_TITLE "\xD6\xC7\xC4\xDC\xD2\xA9\xCF\xE4\xCF\xB5\xCD\xB3"   /* 智能药箱系统 */

/* 不好：依赖源文件编码，一旦被存成 UTF-8 就会显示乱码 */
#define STR_TITLE "智能药箱系统"
```

原因：字符串最终要按 GBK 送到 LCD 字库查字形，显式写字节码可以从根上避免编码依赖。
`main.c` 与 `menu.c` 里的界面字符串都是这么写的。

## 其它文件的编码

| 范围 | 编码 |
|---|---|
| `User/**`（30 个 `.c/.h`） | **GBK** |

## 相关工具

- `tools/convert_to_gbk.py` —— 把源码统一转成 GBK，带「代码签名不变」校验
- `tools/code_signature.py` —— 剥离注释后取代码指纹，用于证明「只改了注释」
- `tools/verify_comments.py` —— 全量验收：编码、代码签名、乱码、注释覆盖
- `tools/gen_font.py` —— 字库生成脚本，输出也是 GBK，且自带中文注释

## 注释规范（本次批量补注释后形成）

- 每个函数：块注释写 **作用 / 参数 / 返回值 / 原理与设计思路**，不只写"做什么"。
- 关键宏与全局变量：用途、单位、取值范围、特殊值含义（如 `0xFF` 表示未设置）。
- 行内注释解释**为什么**这么做，而不是复述代码字面行为。
- 历史坑点（如 ESP-01S 512 字节报文上限、1KB 栈溢出、增量下发协议）在对应代码处注明，
  避免后人重踩。
- 自动生成的文件（`font.c` / `font.h`）不手工加注释，改 `tools/gen_font.py` 让它生成。
